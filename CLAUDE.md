# rfq-from-emails

## What this is

A two-stage pipeline that turns a distributor's RFQ (request-for-quote)
inbox into quote-ready catalog lines:

    <cmd> extract --emails <dir> --out lines.json      # email  -> verbatim line-item strings
    <cmd> match   --lines lines.json --out predictions.json   # line -> catalog sku / abstention
    <cmd> run     --emails <dir> --out predictions.json # OPTIONAL: extract | match in one pass

`data/dev/` holds a worked example set: 18 `.eml` files, `lines.json`
(the reference extraction) and `answer_key.json` (the reference match for
each line). Every rule below was derived by reading all 18 emails against
those two ground-truth files, not guessed from a prose description. The
example set is the spec.

`match` must accept ANY file in the `lines.json` shape — it is designed
to run in isolation on someone else's extraction of a different email
set. `match()` never assumes anything about how `lines.json` was
produced.

## Non-negotiables

- `extract` output is BYTE-VERBATIM. No unicode folding, no dash
  normalization (en-dash `–` stays `–`), no whitespace collapsing, in the
  OUTPUT string. Any normalization exists only inside comparison/parsing
  logic (`normalize.py`), never leaks into the emitted "raw" string. The
  bug to avoid: don't build one `clean()` function that both a comparison
  path and an output path call — the output path must literally slice the
  untouched source text.
- `match` never invents a rounding/substitution the customer didn't
  state. Never auto-substitute a discontinued SKU's replacement.
- No confidence threshold anywhere. `confidence` in the output schema is
  UNSCORED and deliberately unused — a tunable cutoff is exactly the
  overfitting surface this design avoids. Abstention is the only way to
  not commit.
- Don't fit the example set. Every rule below is a general policy with
  example-set evidence attached, not a per-email special case. If a fix
  only makes one email ID pass, it's probably wrong.
- Every design decision is traceable to a specific email ID — cite one
  in the code comment or commit message when in doubt.

## Architecture

    rfq/
      __main__.py    entry point: python -m rfq {extract,match,run}
      cli.py         argparse wiring
      emails.py      .eml -> structured email; MIME, thread/forward
                     detection, sender-domain scoping, rfq-vs-quote
                     classification, dedup/amendment pairing
      extract.py     email -> list[str] verbatim lines (structural
                     readers, prose anchorer, amendment merge)
      normalize.py   THE one place that knows fraction/unicode/unit
                     folding — used by catalog indexing AND query
                     parsing so they can never drift apart
      catalog.py     load catalog.csv + xref.csv; attribute-grid index,
                     family buckets, domain-scoped xref lookup
      parse.py       one raw line -> typed Query (qty, unit word, size,
                     material, family, identifier tokens)
      resolve.py     Query -> filtered catalog rows -> sku / ambiguous
                     / not_in_catalog / discontinued
      quantity.py    qty + stated unit -> qty in the matched sku's uom
      matcher.py     drives resolve() over a whole lines.json; supersedes
    tools/
      score_lines.py   extraction scorer vs data/dev/lines.json
      score_match.py   matching scorer vs data/dev/answer_key.json
      mutate.py        generalization probe: form-preserving rewrites
                       of example lines, measure what breaks
      explain.py       one line in -> full parse + filter trace out
    tests/
    out/               committed outputs, regenerated by the commands
    DECISIONS.md       design memo

Build order (don't start module N+1 until module N is scored, not just
"looks done"):
  1. normalize.py (unit-tested alone, no email/catalog dependency)
  2. catalog.py (manually inspect 5 rows after loading — don't trust
     "loads without error")
  3. emails.py — verify against the 6 trap emails below individually
     BEFORE writing extract.py
  4. extract.py structural readers (csv/html/aligned-table) — score
     against the example set; E008/E009/E011/E014/E017 should be exact
     before any prose logic exists
  5. extract.py prose anchorer — E003/E006/E018
  6. extract.py amendment merge — E010 (check ORDER, not just contents)
  7. tools/score_lines.py + first full example-set score
  8. parse.py + resolve.py + quantity.py (matcher core) + tools/explain.py
     built alongside, not after
  9. tools/score_match.py + first full example-set score
  10. tools/mutate.py — run before declaring done, not as a final checkbox
  11. cli.py / __main__.py wiring, once pieces are independently proven

## Part 1 — extraction rules (example-set evidence)

Email-level classification (get this right BEFORE line-splitting):

| Pattern | Evidence | Rule |
|---|---|---|
| Vendor sends US a price quote | E005 | not an RFQ -> `[]`, even with a clean qty/price table |
| "See attached", nothing attached | E007 | `[]` — MIME has no attachment part |
| CSV attachment present | E008 | rows from the attachment; header row dropped |
| HTML-only email with a table | E009 | rows from `<table>`, joined `" \| "`; header dropped |
| Resend, identical content | E004 (orig) / E013 (resend, later Date:) | later one -> `[]` |
| Amendment, changed content | E003 (orig) / E010 (amendment) | E010 = full reconstructed order: amended item swapped in place, unchanged items copied, new item appended at end |
| Internal forward | E015 (an internal address forwarding a customer) | lines from the quoted CUSTOMER block, not the ISR's note |
| Quoted history, not being amended | E011 (quotes an unrelated already-approved quote) | ignored entirely |
| References untraceable external context | E012 ("same as PO 4471... double it") | `[]` — nothing concrete to quote |

Line-boundary rules (the hard 20%):
- Whitespace INSIDE a row is preserved, not collapsed (E011, E017's
  padded table columns keep every space — no `" ".join()` re-flow).
- Unicode stays unicode in output (E014 keeps `–` and `½` verbatim).
- Parenthetical asides `(...)` are kept whole even when long (E014
  item 17: `(under $25/ea...)` stays).
- Dash-separated TRAILING clauses are dropped only when they're
  commentary: lowercase start, 5+ words, no dimension of their own
  (E002: `"– this is the IronPeak number..."` dropped). A dimension
  anywhere in the segment keeps it (E014 item 17's dash-segment has
  "3/4" in it, so it survives).
- Leading connective ("and"/"also"/"add"...): kept when the fragment
  is glued with no punctuation AND has no product name of its own —
  i.e. elliptical, anaphoric to the previous item (E003: `"and 20 of
  the 3/4″"` needs "black iron 90s" from item 1 to mean anything).
  Dropped when preceded by a comma/hard break and/or wrapped in a
  polite request form ("also can you...") (E003 item 3, E006 all
  three items, E018 item 3). A bare imperative verb directly on a
  self-contained item is kept (E010: `"add 10 of the 1/2 black iron
  caps"`). This is a judgment call, not a clean grammar — it is
  documented as a policy in DECISIONS.md, the fuzziness left visible.
- A correction clause is kept whole, not decomposed (E010: `"make the
  1/2 90s 80 not 50"` stays as one fragment).

## Part 2 — matching rules (answer_key.json evidence)

Design: CONSTRAINT FILTER over catalog.csv's attribute grid, never
similarity/embeddings/fuzzy matching.
    0 survivors  -> not_in_catalog
    1 survivor   -> match (or discontinued, if that row's status is dead)
    >1 survivors -> ambiguous; candidates = the survivors, unmodified

Resolution order — identifier lookup BEFORE attribute filtering:
  1. Is this string (or a token in it) a known sku, or a xref
     alt_number valid for this sender's domain? -> resolve directly,
     even if the row's status is dead -> discontinued, offering
     replaced_by as the SOLE candidate, never auto-substituting it.
     (E009-4 types the dead code `EL90-1/2-GALV` -> abstain:
     discontinued, candidates: ['EL90-1/2-GV'] — but the SAME physical
     part reached by plain description with no material stated (E002-1)
     is just one of 4 live `ambiguous` candidates; the discontinued row
     doesn't even appear there. Identifier-lookup and description-lookup
     are different code paths, not the same filter with a flag.)
  2. Otherwise: parse stated attributes and filter the catalog.

Hard vs soft constraints:
  - MATERIAL named, matches no candidate -> not_in_catalog (E014-19:
    "3/4 PVC ball valve", zero PVC ball valves exist -> 0 candidates,
    no nearest-material substitution)
  - Unmatched tokens with no catalog attribute correspondence are
    IGNORED, not treated as constraints (the "25" in "under $25/ea"
    is not a filter)
  - Two explicitly-named options -> candidates are exactly those two,
    not the whole family (E002-4: "1/2 or 3/4 threaded" -> candidates
    = [BV-1/2-BR-FNPT, BV-3/4-BR-FNPT] only)
  - Candidate COUNT is mechanically derived from what rows exist, not
    curated (E002-1 ambiguous/4-candidates vs E014-12 ambiguous/
    3-candidates — same elbow, same "no material stated" case, but
    EL90-3/4-GV doesn't exist as a row so it can't be a candidate)

xref scoping (rfq/catalog.py):
  - `source = customer:<domain>` valid ONLY for mail from that domain
  - `source = competitor:*` or `legacy` valid for ANY sender
  - internal forwards resolve domain-scoping against the ORIGINAL
    forwarded sender, not the ISR

Quantity/UOM:
  - Stated unit word ("reels", "boxes", "pairs") is EVIDENCE -> route
    straight to that UOM's sku variant (E017-2: "2 reels" -> RL sku
    directly, no conversion)
  - No unit word -> customer means the base unit -> map to base-unit
    sku, convert if needed (m->ft × 3.2808, qty_tol 0.05 — this is a
    real unit conversion, not a count) (E006-1: "30 meters" -> qty
    98.4, uom FT)
  - No base-unit sku exists at all (nuts/washers/lock-washers are
    BX-only; THHN wire is RL-only) -> pack-divide the stated number
    regardless of whether a pack word was said, qty_tol 0, no hedge
    (E014-7: "400 flat washers" -> qty 4, uom BX)
  - BOTH a base-unit and pack sku exist, bare number, NO unit word ->
    ambiguous, not a guess ("a unit word is evidence; its absence when
    both fit is ambiguity"). Not exercised by name in the example set;
    implemented anyway.
  - Vague quantifier ("a couple") -> qty: null
  - Doesn't divide evenly into the pack -> qty: null, NEVER round —
    that's a question for the customer, not us

`why` field: one line, evidence a human can verify in <5 seconds, no
hedging. "exact size+material token match; single candidate", "no PVC in
catalog". Name the attribute that decided it — not a narrative.

Interface limit (documented in DECISIONS.md, not patched around):
E017-1's reference answer needs `qty:null` because the SUBJECT line
conflicts with the table row's qty — but `match()` only ever sees the
bare "raw" string per the `lines.json` contract, never the subject or
any other email context. This is unresolvable inside `match()` by
construction; only `run()` (which has the whole email) could fix it. Do
not special-case subject-sniffing into `parse.py` — document the
interface limit honestly instead.

`supersedes`: optional, UNSCORED. Implemented simply (line-overlap
heuristic across emails in the same batch); DECISIONS.md says plainly
it's best-effort — not over-invested relative to the two core stages.

    python tools/score_lines.py --pred out/lines.json --key data/dev/lines.json --detail

    python tools/mutate.py --detail
    python -m pytest tests/ -q

    E005 / E007 / E011 / E012 / E013 / E015   the six classification traps
